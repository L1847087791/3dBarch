# Three.js 性能原理深度解析

## 一、核心问题

> **为什么在 Step 1 和 Step 2 没有减少 Draw Call 的情况下，帧率就已经显著提升了？**

这个问题揭示了一个常见的误解：**Draw Call 并不是影响 3D 渲染性能的唯一因素**。

## 三、Step 1 共享 Material 为什么提升性能？

### 3.1 GPU 状态机原理

GPU 是一个**状态机**，渲染前需要设置各种状态：

```
渲染 Mesh A (材质 A)          渲染 Mesh B (材质 B)
       │                            │
       ▼                            ▼
┌──────────────────┐         ┌──────────────────┐
│ 设置着色器程序    │         │ 切换着色器程序    │  ◄── 昂贵！
│ 设置 uniform     │         │ 设置新 uniform   │  ◄── 昂贵！
│ 设置混合模式     │         │ 切换混合模式      │  ◄── 昂贵！
│ 绑定纹理        │         │ 重新绑定纹理      │  ◄── 昂贵！
└──────────────────┘         └──────────────────┘
       │                            │
       ▼                            ▼
    Draw Call                   Draw Call
```

**关键洞察**：即使 Draw Call 数量相同，频繁的状态切换也会严重影响性能。

### 3.2 共享 Material 的优化效果

```
优化前：16,160 个不同的 Material 实例
─────────────────────────────────────
渲染 Mesh 1 → 设置材质状态 → Draw
渲染 Mesh 2 → 切换材质状态 → Draw  ◄── 状态切换
渲染 Mesh 3 → 切换材质状态 → Draw  ◄── 状态切换
...
每次都可能触发 GPU 状态切换

优化后：3 个共享的 Material 实例
─────────────────────────────────────
设置外壳材质状态 →
  渲染 Mesh 1 → Draw
  渲染 Mesh 2 → Draw  ◄── 无状态切换！
  渲染 Mesh 3 → Draw  ◄── 无状态切换！
  ...
切换到内层材质状态 →
  渲染所有内层...
```

### 3.3 减少 JavaScript 对象

```javascript
// 优化前：16,160 个 Material 对象
for (let i = 0; i < 16160; i++) {
  const material = new THREE.MeshPhongMaterial({...}); // 创建对象
  // 每个 Material 包含：
  // - 多个属性对象（color, emissive 等）
  // - uniforms 对象
  // - 着色器引用
  // 估计每个 Material 占用 1-2 KB 内存
}
// 总内存：约 16-32 MB 仅用于材质对象

// 优化后：3 个 Material 对象
const SharedMaterials = {
  outerShell: new THREE.MeshBasicMaterial({...}),
  innerLayer: new THREE.MeshPhongMaterial({...}),
  edges: new THREE.LineBasicMaterial({...})
};
// 总内存：约 3-6 KB
```

### 3.4 减少 GC（垃圾回收）压力

JavaScript 引擎的垃圾回收是 **Stop-the-World** 的：

```
┌────────────────────────────────────────────────────────────┐
│                    帧时间线                                 │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  优化前（大量对象）：                                        │
│  ├─渲染─┤ ├─GC─┤ ├─渲染─┤     ├─GC─┤ ├─渲染─┤              │
│  0ms   16ms    32ms    48ms      64ms    80ms              │
│              ↑                    ↑                        │
│          帧率下降              帧率下降                      │
│                                                            │
│  优化后（少量对象）：                                        │
│  ├─渲染─┤├─渲染─┤├─渲染─┤├─渲染─┤├─渲染─┤├─渲染─┤            │
│  0ms   16ms   32ms   48ms   64ms   80ms   96ms             │
│          ↑      ↑      ↑      ↑      ↑      ↑              │
│        稳定 60 FPS                                         │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

## 四、Step 2 几何体缓存为什么提升性能？

### 4.1 几何体创建的隐藏成本

创建一个 `BoxGeometry` 涉及大量计算：

```javascript
new THREE.BoxGeometry(width, height, depth)
// 内部执行：
// 1. 计算 24 个顶点坐标（6面 × 4顶点）
// 2. 计算 24 个法线向量
// 3. 计算 24 个 UV 坐标
// 4. 创建 36 个索引（6面 × 2三角形 × 3顶点）
// 5. 创建 BufferAttribute 对象
// 6. 分配 TypedArray 内存
```

**优化前**：8000 个内层 × 重复计算 = 巨大的初始化开销

**优化后**：相同尺寸只计算一次，后续复用

### 4.2 内存占用对比

```
单个 BoxGeometry 内存占用：
- positions: 24 顶点 × 3 分量 × 4 字节 = 288 bytes
- normals:   24 顶点 × 3 分量 × 4 字节 = 288 bytes
- uvs:       24 顶点 × 2 分量 × 4 字节 = 192 bytes
- indices:   36 索引 × 2 字节 = 72 bytes
- 对象开销：约 200 bytes
────────────────────────────────────
总计：约 1 KB / 几何体

优化前：8000 个几何体 × 1 KB = 8 MB
优化后：3 个几何体 × 1 KB = 3 KB
```

### 4.3 GPU 缓冲区复用

```
优化前：每个几何体独立上传到 GPU
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Geom 1  │───►│ VBO 1   │    │         │
├─────────┤    ├─────────┤    │         │
│ Geom 2  │───►│ VBO 2   │    │  GPU    │
├─────────┤    ├─────────┤    │  显存   │
│ Geom 3  │───►│ VBO 3   │    │         │
├─────────┤    ├─────────┤    │         │
│  ...    │    │  ...    │    │         │
└─────────┘    └─────────┘    └─────────┘
               8000 个 VBO

优化后：共享几何体，单次上传
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Geom 1  │───►│ VBO 1   │───►│         │
└─────────┘    └─────────┘    │  GPU    │
     ↑                        │  显存   │
所有 Mesh                      │         │
引用同一个                      └─────────┘
               3 个 VBO
```

## 五、Draw Call 的真正开销

### 5.1 Draw Call 是什么？

Draw Call 是 CPU 向 GPU 发送的绘制指令：

```
CPU                          GPU
 │                            │
 │  glDrawArrays(...)         │
 │ ─────────────────────────► │
 │                            │
 │  "我准备好了这些数据，      │
 │   请按照当前状态渲染"       │
 │                            │
```

### 5.2 Draw Call 的真正瓶颈

Draw Call 本身的 CPU 开销很小（约 1-10 微秒），**真正的瓶颈是**：

1. **驱动程序验证**：每次 Draw Call 前，驱动程序需要验证当前状态
2. **状态切换**：材质、几何体、纹理等切换
3. **数据同步**：CPU-GPU 之间的数据同步点

```
┌────────────────────────────────────────────────────────────┐
│                  Draw Call 时间分解                         │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  │◄────── Draw Call 前置开销 ──────►│◄─ 实际绘制 ─►│        │
│  │                                  │              │        │
│  ├─────────┬─────────┬─────────────┼──────────────┤        │
│  │ 状态验证 │ 状态切换 │ 数据上传    │   GPU 渲染   │        │
│  │  (小)   │  (大)   │   (可变)    │    (并行)    │        │
│  └─────────┴─────────┴─────────────┴──────────────┘        │
│                                                            │
│  共享材质/几何体 = 减少"状态切换"开销                         │
│  InstancedMesh = 减少"Draw Call 数量"                       │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 5.3 为什么 InstancedMesh 如此高效？

```
普通渲染（16,160 次 Draw Call）：
─────────────────────────────────
CPU: [准备1][调用1][准备2][调用2][准备3][调用3]...[准备16160][调用16160]
GPU:        [绘制1]      [绘制2]      [绘制3]              [绘制16160]
     │◄─────────────── CPU 瓶颈：大量时间花在准备和调用 ──────────────►│

InstancedMesh（1 次 Draw Call）：
─────────────────────────────────
CPU: [准备][调用]
GPU:       [绘制实例1][绘制实例2][绘制实例3]...[绘制实例16160]
     │◄──►│◄───────────────── GPU 并行处理 ───────────────────────────►│
      很短               GPU 满载运行
```

## 六、性能瓶颈诊断指南

### 6.1 如何判断瓶颈在哪？

| 症状 | 可能的瓶颈 | 验证方法 |
|------|-----------|----------|
| 帧率不稳定，有周期性卡顿 | GC 压力 | 查看 Chrome DevTools Memory |
| 帧率稳定但低 | GPU 瓶颈 | 降低分辨率看帧率是否提升 |
| 初始化慢，运行流畅 | CPU 初始化 | Profile 初始化阶段 |
| 交互时卡顿 | CPU 计算/Draw Call | Profile 交互逻辑 |

### 6.2 Chrome DevTools 性能分析

```
1. 打开 DevTools → Performance 标签
2. 录制几秒钟
3. 查看：
   - Scripting（黄色）：JavaScript 执行时间
   - Rendering（紫色）：布局和绘制时间
   - GPU（绿色）：GPU 处理时间

如果 Scripting 占比高 → CPU 瓶颈
如果 GPU 占比高 → GPU 瓶颈
```

### 7.1 当前优化后的理论上限

基于 InstancedMesh 的硬件限制：

| 硬件层级 | 柱状图数量 | 层级数 | 总实例数 | 预期帧率 |
|---------|-----------|--------|---------|---------|
| 低端集显 | 200 | 50 | 10,000 | 30+ FPS |
| 中端独显 | 500 | 50 | 25,000 | 60 FPS |
| 高端独显 | 2,000 | 50 | 100,000 | 60 FPS |
| 专业显卡 | 10,000+ | 50 | 500,000+ | 60 FPS |

### 7.2 限制因素分析

```
┌─────────────────────────────────────────────────────────────┐
│                    性能上限决定因素                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. GPU 顶点处理能力                                         │
│     ├── 每个 BoxGeometry = 24 顶点                          │
│     ├── 100,000 实例 = 2,400,000 顶点/帧                    │
│     └── 现代 GPU 可处理数千万顶点/帧                          │
│                                                             │
│  2. GPU 显存                                                │
│     ├── InstancedMesh 矩阵数据：64 bytes/实例                │
│     ├── 100,000 实例 ≈ 6.4 MB                               │
│     └── 现代显卡有 4-24 GB 显存                              │
│                                                             │
│  3. CPU 矩阵更新                                             │
│     ├── 每帧更新矩阵的计算开销                               │
│     ├── JavaScript 单线程限制                                │
│     └── 可通过 Web Workers / WASM 优化                       │

│  4. 浏览器 JavaScript 堆限制                                 │
│     ├── Chrome 默认约 4 GB                                  │
│     └── 大量 TypedArray 可能触及限制                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 十、结论

### 10.1 关于 Draw Call 的误解

**误解**：Draw Call 数量是唯一的性能指标

**事实**：
- Draw Call 是重要指标，但不是唯一指标
- 状态切换、内存占用、GC 压力同样重要
- Step 1-2 虽未减少 Draw Call，但消除了材质切换和内存浪费

### 10.2 关于性能上限

**你的理解**：上限取决于硬件，无法突破

**补充**：
- 硬件确实设定了物理上限
- 但软件优化（LOD、剔除、多线程、GPGPU）可以在相同硬件上提升 10-100 倍性能
- 优化的本质是**用更少的计算完成相同的视觉效果**

### 10.3 实用建议

| 实例数量 | 推荐方案 |
|---------|---------|
| < 1,000 | 基础优化（共享材质/几何体）即可 |
| 1,000 - 10,000 | InstancedMesh（当前方案）✓ |
| 10,000 - 100,000 | + LOD + 视锥剔除 |
| 100,000 - 1,000,000 | + GPGPU + Web Workers |
| > 1,000,000 | 考虑 WebGPU 或原生应用 |
